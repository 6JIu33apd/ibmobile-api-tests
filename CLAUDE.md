# CLAUDE.md

Контекст проекта для Claude Code. Устройство и запуск — в README.md; здесь — правила работы, знание о бэке
и история решений. Записано актуальное состояние: решения, которые потом поменялись, отмечены «было → стало».

## Правила работы

- **Просто — база.** Самое простое решение, пока оно не создаёт проблем. Думать долго, код писать короткий.
  Не повышать уровень абстракции без необходимости, без лишнего кода и данных.
- **Ничего не придумывать.** Ни параметров, ни конфигов, ни поведения бэка. Не знаешь — спроси или проверь на dev.
- **Код похож на соседний:** код и имена на английском, комментарии, Allure, имена кейсов и документация — на русском.
  Комментарии короткие, по делу.
- **Не запускать ничего на prod.** Тесты гонять на dev.
- **Коммит и пуш — только по команде «коммить и пуш».** Ветка `main`, в конце сообщения
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Перед коммитом проверить, что нет логинов и паролей:
  `git grep -nE "password=[^.<]"` и поиск реального логина.
- Секреты — только в `~/.ibmobile/secrets.properties`, вне репозитория. Ничего не маскировать (ни в Allure, ни в логах).
- `postman/` — коллекция с реальными счетами и картами, в git не попадает.
- Не проверять «ради проверок». Фокус — контракт и бизнес-логика.
- README — только про фреймворк, без бизнес-пояснений: читатели знают домен. Домен — сюда, в CLAUDE.md.
- Не проверять остатки и движение денег.
- Не подбирать коды подтверждения: попытки ограничены. SMS-код принимается только после `send_confirm_sms`.
- Не тестировать неверный пароль реальных профилей: 5 попыток → блокировка без сброса.
- Терминология счетов: дебетовый, кредитный, текущий, депозитный. **Не говорить «карточный» и «расчётный».**
  Слово `Kind` не использовать (для пользователя это «добрый») — `Type`.

## Бэкенд

- Java, REST/JSON, ~100 ручек. Swagger нет — схемы пишем сами.
- Base URL (только http):
  - dev `http://www.avangard.ru/ibMobile_develop/REST`
  - test `http://www.avangard.ru/ibMobile_test/REST`
  - prod `http://www.avangard.ru/ibMobile/REST`
- Почти все ручки POST; немного GET (без ticket); один DELETE — логаут.
- Тело — URLENC; MULTIPART — `prepare_doc` и немногие другие. `prepare_doc` ≥ 7.6 принимает только multipart
  (urlenc → «Unsupported Media Type»).
- Пути версионированы (`Auth/ticket/9.4`). На релиз — одна версия ручки, старые версии поддерживаются.
  Текущий релиз бэка — 3.20.
- `uid` — 15-значный рудимент, бэк принимает любой; шлём `594874414557102`.
  Без `uid` некоторые ручки отдают HTTP 500.

### Авторизация

- Логин: `POST Auth/ticket/9.4` (`login`, `password`, `uid`) → `ticket`. Ticket живёт от 15 минут до 3 часов.
- Ticket передаётся form-параметром `ticket` в каждом запросе.
- Логаут: `DELETE Auth/ticket/9.0` с ticket в теле → `{"responseCode":0}`; после него ticket → errorCode 5.
- Мультисессия — только на dev. На test и prod — одна сессия на логин, поэтому там 1 поток.
- Вход по номеру карты и кодовому слову возвращает логин и пароль (сложный кейс, пока не делаем).

### Ошибки

- Всё приходит с HTTP 200. HTTP не 200 — сбой нижнего уровня.
- Эталонная бизнес-ошибка: `responseCode -1`, `resultCode FAILED`, `checkResult[{badItem, errorMessage}]`.
- Допустимые технические ошибки — только errorCode 1 `authorization_required`, 4 `invalid_parameters`,
  5 `session_expired` (формат с `resultCode`/`resultMessage`), 1000 «Некорректный логин или пароль пользователя.».
- Любой другой errorCode (например, 2 `internal_server_error`) и HTTP не 200 — ошибка сервера, роняет любой тест.

### Документы

- Документ — всё, что меняет данные. Всегда `prepare_doc` с `doc_type`.
- Поток: `prepare_doc` (`doc_type`, `doc_content` — JSON-строкой; файлы — части `file` + `attachmentsList`)
  → подтверждение способом из `authMethods` → `send_doc` с `secure`.
- `send_doc` не принимает id документа: документ живёт в сессии 5 минут.
- Способы: `NONE` (токен `noneAuthInit.code`); `SMSPWD` — `send_confirm_sms`, затем два `secure` (SMS и PWD);
  `SCRETCH` — `show_scretch`, затем код. QR не автоматизируется.
- Безобидные документы без подтверждения: перевод между своими счетами с дебетового, заявление в свободной форме,
  снижение кредитного лимита.
- Коды: dev — SMS `111111`, скретч `11111`, PWD = пароль входа (на dev у всех `1`). test/prod — SMS из Oracle
  открытым текстом; скретч там не используется (в БД хеш).
- «Подобный документ уже обрабатывается в банке.» на `send_doc` — плановый бизнес-отказ (`checkResult` без `badItem`
  + `secureCheck`), защита клиента от дубля. На dev непроведённые документы копятся: пользователь добавит очистку в БД.
  Точное правило дубля неизвестно (вопрос открыт): одинаковый дебетовый перевод с NONE сразу повторно проходил,
  отказы видели на кредитных переводах с SMSPWD.
- Деньги — только `BigDecimal`: double дал `1.5699999999999998`, бэк отклонил.

### Наблюдения на dev

- `ib_our_acc_transfer`: сумма 0 / -1 / без суммы → errorCode 4. Отказы проверок: больше остатка → `amountDeb`
  «Недостаточно средств на счете списания»; тот же счёт → `accCred` «Счет зачисления должен отличаться от счета
  списания»; чужой счёт → `all` «Счет не найден»; 3 знака после запятой → расхождение курса.
- `ib_free_format_statement`: текст возвращается в `doc.text`; пустой текст → `text` «Заполните текст заявления»;
  без текста → `text` «Заполните текст»; вложение без файла → `lobFile` «Ошибка обработки файла-вложения».
- `acc_details/5.0`: `account` берётся из acc_list; без счёта или «123» → errorCode 4; чужой валидный счёт →
  errorCode 2 `internal_server_error` — похоже на дефект, пользователь разбирается сам, кейса нет.
- `prepare_doc` без `doc_type` → HTTP 500.
- Ответ логина содержит ПДн (паспорт, ИНН, телефон); номера карт бэк уже маскирует.
- dev иногда не отвечает (acc_details за 300 с; prepare_doc с вложением — дольше 60 с); перезапуск проходит. acc_list под KILLER не отвечает и за 2 мин (тайм-аут ответа поднят с 60 с до 2 мин) — разбирается.

### Контуры и данные

- dev: тестовые логины, фиксированные коды, деньги не двигаются (списание — логика БД, не наша забота), БД не нужна.
- test: клон прода, только логин пользователя. prod: боевой, только логин пользователя; мутирующие тесты на prod
  разрешены пользователем под своим логином, но запускает их только он.
- Тестовые данные создаёт пользователь («я король базы») — не проектировать их подготовку.
- Профиль `MAIN` на dev: два рублёвых дебетовых, кредитный, рублёвый и валютные текущие, депозитный.
  Валютных дебетовых и кредитных нет — эти кейсы пропускаются.

## Архитектура (кратко)

Пакеты: `config` (Config, Profile, Threads) ← `api` (Endpoint, DocType, Request, ApiResponse, ErrorCode, Session)
← `core` (BaseTest, Login, Template, Confirm, Db) ← `data` (`<Ручка>Data`) ← `tests` (Section, тесты); `tools` (SchemaDraft).

- Одна ручка — один тестовый класс, кейсы — параметры; в каждом классе есть негативные кейсы.
- Сессия — одна на тест: `BaseTest.session()` логинится при первом обращении, логаут после теста. Профиль `MAIN`,
  другой — `@Login(Profile.X)` на методе. Причина: одна ручка разным пользователям отдаёт разные данные
  (например, деталка счёта с блокировкой — под пользователем с блокировкой). Логаут в тесте — `session().logout()`.
- Prod-guard в `BaseTest` (`@BeforeEach`): на prod тесты класса без `@Tag("prod")` пропускаются до логина.
- Ошибки сервера отсекает `Request` централизованно.
- Схемы строгие (draft-04, `additionalProperties: false`), путь по версии ручки текущего релиза.
- Тело документа: шаблон `templates/<doc_type>.json` → `ObjectNode`; кейс меняет поля (`Template.set`), таблица кейсов в тесте.
- `data/<Ручка>Data` хранит весь ответ: `path(...)` для любого поля + методы для частых выборок.
  Создаётся в тесте из его сессии: `new AccListData(session())`.
- Allure: `@Epic` — группа функций (`Section`), `@Feature` — ручка/документ, `@Story("Негативные")`.

## История решений

1. **Каркас.** Стек Java 25 / Maven / JUnit 5 / Rest Assured / Allure; один класс на ручку; строгие схемы;
   секреты в `~/.ibmobile`; версии ручек на релиз в `versions/`; профили логинов; 2 потока на dev, 1 на test/prod.
2. **Документы.** Удалён придуманный `multipartSince` → флаг multipart у ручки. Один бизнес-сценарий — один способ
   подтверждения, заданный в кейсе (не e2e; ручки подтверждения — свои классы).
3. **Сессии.** Было: логин перед каждым тестом → стало: одна сессия на класс; профиль по умолчанию `MAIN`,
   аннотация `@Login` — только для нестандартного.
4. **Отчёт.** Allure-результаты чистятся перед прогоном; осмысленные имена кейсов; негативные — `@Story`.
   Было: уровни меню «Сервисы»/«Ещё» → стало: верхний уровень — группы функций.
5. **Негативы.** Было: общий класс `CommonAuthTest` → стало: негативы внутри каждого класса ручки.
   ProdGuard из META-INF перенесён в `BaseTest`.
6. **Ошибки.** Эталон бизнес-ошибки — `checkResult` с `badItem`; допустимые errorCode 1, 4, 5, 1000;
   остальное роняет тест. Убраны проверки остатков. Убран тест `conv_rates`.
7. **Счета.** Терминология дебетовый/кредитный/текущий/депозитный; флаги `cardAcc`/`credit`/`currAcc`/`idepAcc`.
8. **Структура (2026-10-26).** `core` разделён на `config`/`api`/`core`. Было: `config.properties` с uid, env, release,
   threads → стало: всё о контуре в `env/<env>.properties`, умолчания в `Config`, uid — константа в `Request`.
   `Template` заменён на Jackson `ObjectNode`. Было: `data.Accounts` с `Kind` → стало: `AccListData` с `AccountType`.
9. **Данные и кейсы (2026-10-27).** `AccListData` хранит весь ответ. Перевод между своими
   счетами — любые два счёта **одной валюты** (разные валюты — конвертация, отдельный документ позже).
   Негативы — таблицы кейсов (`@MethodSource`) поверх валидного тела по умолчанию. Тайм-ауты: 10 с / 60 с (позже ответ — 2 мин).
10. **Сессия на тест (2026-10-27).** Было: сессия на класс → стало: сессия на тест, `@Login` на методе, данные
    из других ручек берутся в тесте. Кейс, зависящий от данных сессии («на тот же счёт»), — отдельный метод,
    таблицы `@MethodSource` — статические. Из README убраны бизнес-пояснения.
11. **Единый дизайн классов (2026-10-27).** Ручки и документы устроены одинаково: позитивные → таблица
    `invalidParameters` → таблица `rejections` → особые кейсы → `withoutTicket` → валидный запрос по умолчанию внизу.
    `Request.param(name, null)` убирает параметр (как `Template.set` для полей документа).
12. **Документы (2026-10-27).** Было: класс `Doc` → стало: `PrepareDoc` (`content`, `set`) и `SendDoc`
    (`Confirm`). Константа типа документа в тестах — `DOC_TYPE`, переменные — `docType`.
13. **Любая ручка — через `Request.to()` (2026-10-27).** Отправляет только `Request` (`post`, `delete`; внутренний
    `execute`). Было: классы-обёртки `PrepareDoc`/`SendDoc` → стало: prepare_doc и send_doc вызываются как все ручки,
    `Request.to(PREPARE_DOC)` / `Request.to(SEND_DOC)`. Остались помощники данных: `Template` (`of`, `set`, `attachments`)
    и enum `Confirm` с `secure(session, prepared)` (сам запрашивает код через send_confirm_sms / show_scretch).
    В тестах нет обёрток над запросом, только данные по умолчанию (`account(type)`, `content()`); кейс = `Request.to`
    + `.as(session())` + изменение (`.param` / `Template.set`) + `.post()` + проверки; «без ticket» — без `.as`.
    Удалён неиспользуемый `Session.login(login, password)`; сортировка по `otb` — через `BigDecimal`.
14. **DocType (2026-10-27).** Было: `doc_type` строкой в каждом классе → стало: enum `api/DocType` (значение — имя
    в нижнем регистре; документов больше 30, добавляются по мере тестов), в классе `DOC_TYPE`.
    Аннотация на класс не нужна: тип всё равно передаётся в `param`, схему и шаблон. `matchesSchema(DocType)`.
15. **Документы параллельно (2026-10-27).** Было: `@Execution(SAME_THREAD)` на классах документов (тогда сессия была
    общей на класс) → стало: убрано — сессия на тест, документ живёт в сессии своего теста. Проверено на dev:
    3 прогона документов в 2 потока, кейсы пересекались по времени, всё зелёное. Убран неиспользуемый `@Tag("mutating")`.
    Lombok не добавляем: сэкономил бы ~20 строк (конструкторы enum и `ApiResponse`, приватные конструкторы утилит)
    ценой зависимости, настройки annotation processor под Java 25 и плагина IDE.
16. **`Request.doc` (2026-10-27).** `Request.doc(docType, content, files...)` ставит `doc_type`, `doc_content`,
    прикладывает файлы и заполняет `attachmentsList` — вызов prepare_doc в одну строку, по-прежнему `Request.to(PREPARE_DOC)`.
    Удалены `Template.attachments` и публичный `Request.file`.
