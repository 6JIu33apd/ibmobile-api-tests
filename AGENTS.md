# AGENTS.md

Инструкции и контекст проекта для Codex: правила работы, знание о бэке, неочевидное в коде, подводные камни и решения,
к которым не возвращаться. Устройство фреймворка, запуск и примеры — в README.md (читать при работе с кодом).

## Проект

Контрактные API-тесты бэкенда розничного интернет-банка «Авангард» (ibMobile, Java, REST/JSON, ~100 ручек).
Репозиторий `https://github.com/6JIu33apd/ibmobile-api-tests`, ветка `main`, локально
`C:\Users\6JIu33apd\Documents\Idea\ibmobile-api-tests` (Windows 11, IDEA, Git Bash / PowerShell, `git core.autocrlf=true`).
Стек: Java 25, Maven (`mvnw`), JUnit 6.1.3, Rest Assured 6.3.0 (+ json-schema-validator; Groovy 5, httpclient 4.5),
Allure 3.0.1 (`allure-jupiter` — бывший `allure-junit5`; `Allure.attachment` вместо `addAttachment`; запрос и ответ —
одно вложение «HTTP exchange»), отчёт 2.46.1 через allure-maven 3.1.0 (история прогонов — в `.allure/history`),
AssertJ 3.27.6, Jackson 2.22.4, ojdbc11 23.26.3.0.0, surefire 3.5.6.
`dependency:analyze` — только плагином ≥ 3.9.0 (3.7.0 не читает байт-код Java 25); его «unused» для `junit-jupiter`,

## Правила работы

- **Просто — база.** Самое простое решение, пока оно не создаёт проблем. «Думай долго, код пиши короткий».
  Не повышать уровень абстракции без необходимости, без лишнего кода, данных и обёрток. Удалять неиспользуемое.
- **Ничего не придумывать** — ни параметров, ни конфигов, ни поведения бэка, ни причин в комментариях.
  Не знаешь — спроси или проверь на dev (прогоном, а не догадкой). Пользователь ловит выдумки сразу.
- **Давать рекомендацию, а не обзор вариантов.** Если пользователь предлагает решение хуже — сказать прямо, почему, и сделать лучшее; он это принимает.
- **Код похож на соседний:** код и имена — на английском; комментарии, Allure, имена кейсов, README, AGENTS.md
  и ответы пользователю — на русском. Комментарии короткие заметки по делу, только где неочевидно.
- **Не запускать ничего на preprod и prod.** Тесты с `@PreProd` / `@Prod` гоняет только пользователь; `mvnw test` их
  и так исключает (pom), `-Pall-envs` и `-DexcludedGroups=` самому не использовать.
- **После изменений показывать, на сколько строк стало больше или меньше** (всего и по коду/ресурсам/докам).
  Для Java всегда указывать число строк до и после изменений.
- **Коммит и пуш — только по команде «коммить и пуш».** Ветка `main`, сообщение на английском. Перед коммитом — проверка на секреты:
  `git grep -nE "password=[^.<]|<реальный логин>"` (ожидаемые совпадения — только примеры команд в AGENTS.md).
  Реальные логины профилей в репозиторий не писать (ни в код, ни в AGENTS.md).
- **Правки пользователя не трогать** и не пересказывать их в каждом ответе: проверять и говорить, только если что-то
  не так (например, после снятия `@Login` остались неиспользуемые импорты — убрать и коротко сказать).
- **Изменяемые параметры — не в Java**, а в ресурсах/`-D`: перезапуск без правки кода, переезд в переменные CI.
- **Отчитываться честно:** сколько тестов прошло/упало/пропущено и почему; сбой соединения отличать от бага кода.
  При тайм-аутах и ошибках соединения тесты не перезапускать: пользователь работает под VPN. Не коммитил — так и написать.
- Настройки и секреты контуров — только в `~/.ibmobile/dev.properties`, `preprod.properties`, `prod.properties`, вне репозитория.
  Ключи без префиксов; версии ручек остаются в ресурсах. **Ничего не маскировать** (ни в Allure, ни в логах).
- `postman/` — коллекция с реальными счетами и картами, в git не попадает (в .gitignore).
- **Не проверять «ради проверок».** Фокус — контракт и бизнес-логика; мусорный ввод на каждое поле не нужен.
  Для новой ручки — успешный кейс и негативные; граничные значения и мелочи пользователь делает сам.
- **Не решать, что бэк должен отвечать.** Кейс фиксирует то, что бэк отвечает сейчас (проверено на dev).
  Только http — так есть, не поднимать.
- **README — только про фреймворк, без бизнес-пояснений:** читатели знают домен. Домен — сюда, в AGENTS.md.
- Не проверять остатки и движение денег. Не писать e2e: один бизнес-сценарий — один способ подтверждения.
- Не подбирать коды подтверждения: попытки ограничены. SMSPWD: `check_password/1.1` → `send_confirm_sms/1.1` → `send_doc`.
- Не тестировать неверный пароль реальных профилей: 5 попыток → блокировка без сброса. Негатив логина — только
  несуществующий логин. Одноразовые профили для блокировок пользователь даст позже.
- Терминология счетов: дебетовый, кредитный, текущий, депозитный. **Не говорить «карточный» и «расчётный».**
  Слово `Kind` не использовать (для пользователя это «добрый») — `Type`.
- Тестовые данные создаёт пользователь («я король базы») — не проектировать их подготовку.
- Профиль KILLER — для своих нужд (образцы для схем и т. п.), в тесты не добавлять.

## Бэкенд

- Base URL (только http, без https):
  - dev `http://www.avangard.ru/ibMobile_develop/REST`
  - preprod `http://www.avangard.ru/ibMobile_test/REST`
  - prod `http://www.avangard.ru/ibMobile/REST`
- Почти все ручки POST; немного GET (публичные, без ticket); один DELETE — логаут.
- Тип тела задаётся в `Endpoint` и применяется в `HttpFilter`. `prepare_doc` ≥ 7.6 принимает
  только multipart (urlenc → «Unsupported Media Type»).
- Пути версионированы (`Auth/ticket/9.4`, `Doc/prepare_doc/8.1`). На релиз — одна версия ручки, старые версии
  поддерживаются. Обычно от релиза к релизу меняются 1–2 ручки. Текущий релиз бэка — **3.20**.
- `uid` — 15-значный рудимент («сраный рудимент»), бэк принимает любой; шлём `594874414557102`.
  Без `uid` некоторые ручки отдают HTTP 500 (видели на conv_rates).
- Ответы большие (сотни строк). Номера карт бэк уже маскирует (`999999******9999`).

### Авторизация

- Логин: `POST Auth/ticket/9.4` (`login`, `password`, `uid`) → `ticket` + данные клиента (ПДн: паспорт, ИНН, телефон;
  `clientInfo.sessionTimeout=1800`). OTP при логине нет.
- Ticket передаётся form-параметром `ticket` в каждом запросе. Живёт от 15 минут до 3 часов.
- Логаут: `DELETE Auth/ticket/9.0` с ticket в теле → `{"responseCode":0}`; после него ticket → errorCode 5.
- Мультисессия — только на dev (тестовые логины). На preprod и prod — одна сессия на логин, поэтому их тесты идут по одному.

### Ошибки

- Всё приходит с HTTP 200. HTTP не 200 — сбой нижнего уровня.
- Эталонная бизнес-ошибка (отказ проверок): `responseCode -1`, `resultCode FAILED`, `resultMessage`,
  `checkSuccess false`, `checkResult[{priority, badItem?, type, error, warning, info, errorMessage}]`,
  у send_doc ещё `secureCheck {errorExist}`, иногда `authMethods`. Схема — `schemas/errors/check_failed.json` (ручная).
- Допустимые технические ошибки — только errorCode 1 `authorization_required` (нет ticket), 4 `invalid_parameters`,
  5 `session_expired` (ещё обязательные `resultCode=FAILED`/`resultMessage`), 1000 «Некорректный логин
  или пароль пользователя.». `ResponseCheck.error()` проверяет `schemas/errors/error.json`: обязательны `errorCode`/`errorDesc`, поля `resultCode=FAILED`/`resultMessage` опциональны.
- Любой другой errorCode (например, 2 `internal_server_error`) и HTTP не 200 — ошибка сервера, роняет **любой** тест,
  в том числе негативный («Ошибка сервера: …»). Сервер не должен отдавать 500.
  Ошибка автоматического логаута — исключение: остаётся в HTTP-шаге Allure, не меняя результат теста.

### Документы

- Ручки бывают информационные, мутирующие без подтверждения (`change_login`, `change_password`) и документы
  с подготовкой через `prepare_doc` и выбранным способом подтверждения. Типов документов больше 30.
- Поток: `prepare_doc` (`doc_type`, `doc_content` — JSON-строкой; файлы — части `file` + описание в `attachmentsList`
  с `filename`, `contentType`) → подтверждение способом из `authMethods` ответа → `send_doc` с `secure`.
- `send_doc` не принимает id документа: подготовленный документ живёт 5 минут и хранится **общим для всех ticket
  логина** (проверено двумя сессиями MAIN: prepare_doc в B перетёр документ A → `send_confirm_sms` в A — errorCode 4).
  Одновременные prepare_doc одного логина иногда дают errorCode 2. Поэтому классы документов —
  `@ResourceLock("prepared_doc")`, идут по одному (prepare_doc в негативах тоже перетирает документ).
- `secure` — JSON-строка `{"authMethod":"...","authToken":"..."}`. Способы: `NONE` (токен `noneAuthInit.code`);
  `SMSPWD` — POST `Auth/check_password/1.1` (uid, ticket, password) → POST `Auth/send_confirm_sms/1.1` (uid, ticket), затем **два** `secure` (SMS, PWD); `SCRETCH` —
  `show_scretch`, затем код. QR не автоматизируется. С кредитного счёта authMethod — `QR_OR_SMSPWD_OR_SCRETCH`.
- Безобидные документы без подтверждения (NONE): перевод между своими счетами с дебетового, заявление в свободной
  форме, снижение кредитного лимита.
- Коды SMS и скретча — `sms`/`scretch` в файле контура; PWD — общий `password`. БД для подтверждения не используется.
- Смена логина/пароля убивает ticket. Такие тесты — под отдельными профилями; восстановление исходных данных выполняет сам тест.
- «Подобный документ уже обрабатывается в банке.» на `send_doc` — плановый бизнес-отказ (`checkResult` без `badItem`
  + `secureCheck`), защита клиента от дубля (похожий документ — те же счета и сумма, пока предыдущий обрабатывается).
  На dev непроведённые документы копятся (на dev они не исполняются): пользователь добавит очистку в БД.
  Точное правило дубля неизвестно (вопрос открыт): одинаковый дебетовый перевод с NONE сразу повторно проходил,
  отказы видели на кредитных переводах с SMSPWD. При отправке позитивных переводов использовать случайные суммы (1.01–9.99).
- Деньги — только `BigDecimal`: double дал `1.5699999999999998`, бэк отклонил документ.

### Счета (acc_list)

- Дебетовые и кредитные (флаг `cardAcc`, кредитный — ещё `isCredit` и `credit`, на MAIN равны) могут иметь карты. Карта не существует без счёта
  и лишь прокси: списание всегда со счёта. Текущие (`currAcc`) — только дебетовые, без карт. Депозитные (`idepAcc`) —
  дебетовые, без карт, со своей логикой. Валюта — `currency` (`RUR` — рубли), доступная сумма — `otb`, номер — `code`
  (20 цифр). Список — `accounts.account`.
- Перевод между своими счетами — любые два счёта **одной валюты**; разные валюты — конвертация, отдельный документ (позже).
- Деталка счёта: `Statement/acc_details/5.0` с `account` из acc_list; ответ `accBalanceDetails[0].account`.
  Разные пользователи видят разное (например, блокировки по счёту) — для таких кейсов свой профиль.

### Наблюдения на dev

- `full_history/5.0`: выборка по датам возвращает `dateFrom`/`dateTo`, по странице — `offset`/`limit`/`hasMoreByDate`;
  если переданы обе пары, используется страница. Без `method` история возвращается; `limit=2` заменяется на 10.
  Неполные пары параметров, отсутствие обеих пар и обратный период → errorCode 4; без / несуществующий ticket → 1.
  `acc` фильтрует по `history[].acc` или `accCred`; `debit_or_credit=1` — списания, 2 — зачисления.
  Повторяющийся `doc_type` принимается списком; `www_card_pay` исключается из `docTypes` ответа.
  `srcId` есть не у всех операций; `details` может содержать вложенные операции. Пустая история сохраняет формат выбранного режима.
- `ib_our_acc_transfer` (шаблон `{"amount","accDeb","accCred"}`): сумма 0 / -1 / без суммы → errorCode 4.
  Отказы проверок: больше остатка → `amountDeb` «Недостаточно средств на счете списания»; тот же счёт → `accCred`
  «Счет зачисления должен отличаться от счета списания»; чужой счёт списания или зачисления → `all` «Счет не найден»;
  3 знака после запятой → расхождение курса. Ответ send_doc: `doc.amount`. Повторный send_doc с тем же `secure`
  после успешного → errorCode 4; send_doc без ticket → errorCode 1.
- `ib_free_format_statement` (шаблон `{"text","needConfirm","attachmentsList"}`): текст возвращается в `doc.text`
  (так проверяется UTF-8), вложения — `doc.attachmentsList.filename`; пустой текст → `text` «Заполните текст
  заявления»; без текста → `text` «Заполните текст»; вложение описано, но файл не приложен → `lobFile` «Ошибка
  обработки файла-вложения».
- `acc_details/5.0`: без счёта или «123» → errorCode 4; чужой валидный счёт → errorCode 2 `internal_server_error` —
  похоже на дефект, пользователь разбирается сам, кейса нет.
- Несуществующий ticket (`invalid_ticket`) → errorCode 1 `authorization_required` (не 5).
- `prior_info/6.0` (`doc_type`): данные есть для `ib_pay_rub`, `ib_inside_pay_rub` (`nextDocNumber`, типы документов
  личности), `ib_card_chargeback_statement` (`accountList` с картами `cards[].id`, `chargebackReasons` 1–7),
  `ib_card_order_statement`; для `ib_our_acc_transfer`, `ib_free_format_statement`, `ib_card_block_statement`,
  `ib_card_reissue` → errorCode 4 (не факт, что ручка их поддерживает: в `DocType` есть, в тестах нет);
  без / неизвестный doc_type → 4. Под KILLER chargeback не отвечает за 2 мин (остальные типы отвечают).
- `ib_card_chargeback_statement` (шаблон `{"cardId","description","reasonType","opersList","attachmentsList"}`):
  карта — из prior_info, операция `5931036292` — из образца пользователя (принимается с любой картой MAIN).
  authMethods `QR, SMSPWD, SCRETCH`; скретч на dev проходит с `11111` (`scretchInit.restCount` 3). Отказы:
  без вложения → `all` «Прикрепление документов обязательно» (проверяется раньше остальных полей); вложение без
  файла → `lobFile`; пустое / без `description` → `all` «Заполните description»; без `cardId` → «Заполните cardId»;
  пустой / без `opersList` → «Укажите хотя бы одну операцию». Повторная отправка по той же операции проходит.
  Позитив — по кейсу на каждую причину `reasonType` 1–7 (разные сценарии). Несуществующая операция `1` →
  errorCode 2: кейс `unknownOperation` падает, так и оставить (решение пользователя). `cardId` 0 / чужой и
  `reasonType` 0 / 999 проходят — детальные проверки пишет пользователь. В ответе send_doc `opersList` и
  `opersDetails` удвоены (`[id, id]` при одной операции).
- `prepare_doc` без `doc_type` → HTTP 500.
- `prepare_doc` для перевода между своими счетами и chargeback может вернуть `scretchInit` с `NO_ACTIVE_CARD`,
  `responseCode -1`, без `badCount`, `restCount`, `cardNumber`. Корневой результат остаётся успешным;
  Позитивы кредитного перевода и chargeback используют SMSPWD; для SCRETCH нужна активная скретч-карта профиля.
- dev иногда не отвечает: acc_details висел 300 с, prepare_doc с вложением — дольше 60 с; перезапуск проходит.
  **acc_list под профилем KILLER не отвечает и за 2 мин** (разбирается; тесты под KILLER пользователь снял).

### Контуры и профили

- dev: тестовые логины, мультисессия, фиксированные коды, деньги не двигаются (списание — логика БД, не наша забота),
  БД не нужна. preprod: клон прода, только логин пользователя. prod: боевой, только логин пользователя; мутирующие тесты
  на prod пользователь разрешает под своим логином (операции, невозможные на dev), запускает их только он.
- БД: Oracle, свой JDBC URL на контур. Данные из БД будут браться хранимыми процедурами:
  селекты упакует в пакет процедур пользователь, тесты только вызывают нужную (`Db` — под это, не упрощать).
- Логин по умолчанию — ключ `login`; на dev у него два рублёвых дебетовых, кредитный, рублёвый и
  валютные текущие, депозитный (валютных дебетовых и кредитных нет — эти кейсы пропускаются).
  `@Login("loginextra")` выбирает ключ другого логина. Пароль и коды общие, `Profile` удалён; выбранный логин обязателен.

## Неочевидное в коде

Пакеты `config`, `api`, `core`, `tests`; Session — в `core`, сбор образцов и генерация схем — в `tools/SchemaDraft` (подробно — README).

- **Контур — у теста:** dev по умолчанию, `@PreProd` / `@Prod` (метод или класс) — preprod / prod. `BaseTest` ставит
  `Config.setEnv` (ThreadLocal: тест целиком в одном потоке). В аннотациях мета-`@ResourceLock("<env>")` — тесты preprod и
  prod идут по одному (одна сессия на логин), и `@Tag("<env>")`. Проверено без сети. `release` — во внешнем файле контура.
  Аннотации Login, PreProd, Prod, Negative вложены в BaseTest; он выбирает dev по умолчанию. Config требует контур; @Tag его не меняет.
- Запросы — нативные `given().formParam(...).post(endpoint.path())` (DELETE — только логаут); проверки — статические методы `ResponseCheck`.
  `matchesSchema(response, path)` принимает готовый путь: `endpoint.schema()` для обычной ручки, `endpoint.schema(docType)` — для prepare_doc, prior_info и send_doc.
  `BaseTest` один раз задаёт `RestAssured.config` и `HttpFilter` в статическом блоке; base URL выбирается фильтром на потоке запроса.
  `HttpFilter` добавляет uid, пишет Allure и проверяет HTTP 200, затем вызывает `ResponseCheck` для проверки `errorCode`. Тайм-ауты — 10 с / 2 мин. URLENC кодирует Rest Assured;
  повторные secure — готовые JSON-строки. Multipart-тексты — `text/plain; UTF-8`; Allure получает карту параметров «ключ=значение», файлы описаны в doc_content.attachmentsList.
  Ticket добавляется автоматически из сессии, кроме Auth/ticket (POST) и `.auth().none()`; явно заданный ticket сохраняется.
- Дробные числа ответа — `BigDecimal` (`NumberReturnType.BIG_DECIMAL`): по умолчанию Rest Assured даёт `Float`,
  `12345678.91` → `12345679` (проверено); целые остаются `Integer`.
- Ответы помощников — локальные `JsonPath` или поля экземпляра при общей подготовке в `@BeforeEach`; суммы читаются через `response.jsonPath().getObject(path, BigDecimal.class)`.
- `DocContent.attach` добавляет файлы из classpath `files/` в запрос и заполняет `attachmentsList`.
  Тест заполняет поля формы после добавления вложений и отправляет готовый запрос через `.post()`.
- `Confirm.send(method, prepared)` принимает способ строкой NONE/SMSPWD/SCRETCH, выполняет подтверждение и возвращает ответ send_doc.
  Jackson экранирует пароль. Session отвечает только за вход, ticket и логаут.
  `DocContent.load` читает шаблон, `set` меняет поле по пути.
  В таблицах без параметра — `formParams(value == null ? Map.of() : Map.of(name, value))`; `formParam(null)` не удаляет поле.
- `BaseTest.find(response, path)` выбирает из JsonPath по полному GPath: `null` — пропуск; `response.get(path)` отдаёт значение как есть. Ошибка GPath — ошибка теста.
  У помощников `success` вызывается явно в тесте. У целевой ручки строгая схема покрывает признаки отказа.
- `BaseTest` после `Config.setEnv` передаёт в `Session.open` ключ `@Login` или null; Session выбирает `login` по умолчанию и сразу выполняет вход.
  Сессия — ThreadLocal; каждый `Session.open` заменяет её новой. `loginResponse()` возвращает сохранённый ответ, `ticket()` читает его без запроса; в Allure вход — отдельный шаг перед запросами кейса.
  `Session` — record с ответом входа; `Session.close()` после кейса выполняет логаут только при успешном входе. Ошибка поглощается в этом же методе; HTTP-запрос остаётся в Allure, тест не падает.
  `CURRENT` и контур очищаются в `finally` после кейса. `Config.setEnv(null)` очищает контур.
  Явный `Session.current().logout()` сохранён для контрактного теста логаута; после выхода ticket не обновляется.
- `SchemaDraft` собирает все успешные ответы независимо от утверждённых схем; ошибки и отказы пропускаются.
  Образцы — `.schema-samples/schemas/<endpoint>/[<doc_type>/]<uuid>.json`, снимки накопленной схемы — `.schema-samples/drafts/schemas/` с тем же путём и UUID. Одинаковые тела не дублируются.
  `required` — общие поля всех объектов на каждом уровне; типы объединяются, `null` считается присутствием, пустой `required` не создаётся. Форматирование — стандартный Jackson.
  Каталог `doc_type` определяется только полем текущего запроса для любой ручки, без enum и переноса типа из prepare_doc. Версии отдельно не выделяются; старые каталоги `<version>.json` пропускаются при чтении образцов.
  `-DschemaDraft.skip=true` отключает сбор и генерацию; `capture` синхронизирован для сохранности общей схемы.
  Генератор всегда работает молча: исключения поглощаются, шагов и вложений Allure нет.
  Нужный снимок пользователь переносит в `src/test/resources/schemas` под именем `<версия>.json`; генератор эталоны не меняет. Отложенная генерация и `main` удалены.
- Схемы: draft-04, строгие, без `$ref`; структуры встроены, включая элементы `checkResult` и обе ветки истории. Пустой `required` draft-04 не допускает.
  Массив без `items` ничего не проверяет (`SchemaDraft` не выводит структуру пустых массивов);
  `auth_login` `accounts` и `lastUnreadNewsList` — `maxItems: 0`, пока нет образца с элементами.
- Потоки: `fixed` 2 в `junit-platform.properties`; классы — `concurrent`, кейсы класса и его `Negatives` — `same_thread`
  (проверено по времени в Allure: внутри класса пересечений 0). pom: версии плагинов закреплены; Allure-результаты чистятся на
  `initialize` (иначе копятся между прогонами).
- `Config` кэширует каждый используемый `~/.ibmobile/<env>.properties`, `Endpoint` — `versions/<release>.properties` один раз за прогон.
  Общий Config.load читает переданный источник; не определяет тип файла по имени и не выбирает контур.
  Базовый путь и версия начинаются с `/` (`/Auth/ticket` и `AUTH_LOGIN=/9.4`). `HttpFilter` сопоставляет полный путь и HTTP-метод.
  Пустые значения удаляются при загрузке; непустые строки, включая пробелы в паролях, сохраняются целиком.
  Дополнительные логины читаются из кэша; `Config.get` возвращает обязательное значение текущего контура.
  Файлов `resources/env` и старого `secrets.properties` в загрузке нет; ключ URL — `baseurl` в нижнем регистре.
- `Section` пополняется по мере появления классов — неиспользуемые группы не удалять.

## Окружение и подводные камни

- Запуск: `./mvnw -q test [-Dtest=Класс|'Ib*Test']`; итоги — `target/surefire-reports/TEST-*.xml`
  (атрибуты `tests/errors/skipped/failures`); отчёт — `mvnw allure:serve`. Полный прогон ~2–4 мин.
  `mvnw clean test` удаляет `target`, включая предыдущие XML и classpath-схемы; `.schema-samples` сохраняется.
  `NoHttpResponse` / тайм-аут на dev — сбой соединения, без повторного запуска.
- `java` из PATH падает (access violation) — запускать `$JAVA_HOME/bin/java`; `jshell` в Git Bash падает.
  Classpath: `mvnw dependency:build-classpath -Dmdep.outputFile=...`.
- Правка файлов скриптом Python: `encoding='utf-8'`, `newline='\n'`, `assert count==1`. Write/Edit требуют Read файла.
  JSON-схемы править текстом, не `json.dumps` (формат Jackson `"key" : value` и инлайн-массивы — иначе огромный диф).
  «file changed on disk» после коммита обычно — нормализация CRLF (`autocrlf=true`); проверять `git status`/`git diff`.
- Вывод кириллицы из Python в консоль — кракозябры (cp1251); `awk length` считает байты, а не символы.

## Решения (не возвращаться)

- Сессия — на тест, вход в `BaseTest` через `Session.open`, `@Login("ключ")` на методе (было: ленивый вход, enum Profile; логин в теле теста — пользователь против).
  Ticket передаёт HttpFilter; `.auth().none()` отключает его для одного запроса, в том числе негативного без ticket.
- Фильтр контуров — в pom (`excludedGroups=preprod,prod`, профиль `all-envs`), а не в JUnit: теги фильтрует surefire,
  IDEA запускает выбранный тест на его контуре. Проверено пустыми тестами.
- Контур — у теста (`@PreProd` / `@Prod`); было: `-Denv`/`-Drelease` на прогон, prod-guard по `@Tag("prod")`, `config.Threads`.
- Запросы — нативный Rest Assured, без собственного builder и HTTP-фасадов; `DocContent` готовит документ, `Confirm.send` — подтверждение и отправка.
  Пакет data удалён: ответы — в локальных JsonPath, параметры — в тестовом классе.
  Перегрузки помощников не добавлять. `Endpoint.schema(DocType...)` — один метод на 0/1 аргумент без проверки количества. `DocType` — enum, на класс не вешается.
- Классы doc_type проверяют prepare_doc; SendDocTest удалён, send_doc только помощник для отправки документов. AuthTicketTest объединяет логин/логаут.
  Простым URLENC-ручкам отдельные шаблоны не нужны. Переводы и chargeback отправляются через Confirm.send; схема проверяется только у prepare_doc.
- Один кейс не запускается одновременно на разных контурах; общий doc_content не требует версионирования по контурам. Шаблон ответа — JSON Schema.
- Негативы — в каждом классе (было: общий `CommonAuthTest`). Параметры кейсов — `Arguments[]` с `@FieldSource`, набор полей формы можно передать как `Map`.
- `FullHistoryTest`: данные формы — в классе; период и пагинация проверяются отдельными запросами.
- Allure: верхний уровень — группы функций `Section` (было: «Сервисы»/«Ещё»).
- Негативные — вложенный класс `@Nested @Negative class Negatives` (мета: `@Story`, `@DisplayName`;
  `@Nested` — явно: в мета-аннотации JUnit его видит, инспекция IDEA — нет); было:
  `@Story("Негативные")` на каждом методе. Проверено без сети: Epic/Feature, `@ResourceLock` внешнего класса
  действуют, внешний экземпляр (сессия) — свой на каждый тест. Подкласс вместо вложенного — нет: дубль классов.
- Имена — как у бэка, без сокращений: `docType`, `docContent`, `authMethod`, `authToken`,
  `errorDesc`, `errorMessage`, `accDeb`/`accCred`. Имя кейса передаётся в `argumentSet`.
- Локали не задавать; не добавлять проверки ошибочного использования помощников — ошибки роняют тест обычным исключением.
- Кейсы одной ручки — по очереди, разные ручки — параллельно (решение пользователя: тест живёт в своей сессии,
  на одну ручку — по одному). Через `mode.default=same_thread`, а не `@ResourceLock` на каждом классе.
- `DocContent` (было `Template`, `templates/`): не путать с шаблонами платежа бэка. `set` — путь через точку на
  любую глубину (в doc_content бывает 5 уровней), индекс массива — число, null удаляет поле или элемент.
- Выбор счёта — в тесте условием GPath по полям acc_list (`it.cardAcc && !it.isCredit && it.currency == 'RUR'`);
  было: enum `AccountType` с `typeOf` в `AccListData` — пользователь против модели домена в data-классах.
  `isCredit=false` — ещё и у текущих и депозитных: «дебетовый с картами» — `cardAcc && !isCredit`.
- Документы — по одному (`@ResourceLock("prepared_doc")` на классе): было «параллельно, проверено 3 прогонами» —
  проходило по случайности расписания; `-Dtest=IbOurAccTransferTest#transfer` падал каждый раз.
- Не делаем: Lombok (зависимость и annotation processor не стоят ~20 строк), автоперезапуск упавших (скроет
  зависания dev и повторит мутирующие документы), смену json-schema-validator (draft-04 хватает), общие `$ref` для
  блоков ответа prepare_doc (каждую схему от `SchemaDraft` пришлось бы править руками), проверки остатков, `conv_rates`.
- Удалено придуманное: `multipartSince`, `@Tag("mutating")`.
