# AGENTS.md

Контрактные API-тесты розничного банка «Авангард» (ibMobile). Перед правками прочитать `README.md`.
Версии зависимостей — в `pom.xml`, ручек — в `src/test/resources/versions/`. README описывает фреймворк, доменные наблюдения храним здесь.

## Работа в репозитории

- Самостоятельно запускать **только dev** командой `.\mvnw.cmd test`. Тесты `@PreProd` и `@Prod`, профиль `-Pall-envs` и снятие `excludedGroups` — только для пользователя.
  При тайм-ауте или ошибке соединения прогон не повторять (VPN).
- Сохранять правки пользователя. Любые дополнения за пределами запроса сначала согласовать. Код и идентификаторы — на английском, пояснения, кейсы, Allure и ответы — на русском. Давать одну рекомендацию.
  Писать в стиле соседнего кода, удалять лишнее. Ориентир для метода — до 20 строк. Новые помощники в ядре сначала согласовать.
- Поведение ручки подтверждать на dev. Покрывать контракт, позитив и основные отказы. Границы и детальные проверки пишет пользователь.
  Один сценарий — один способ подтверждения. Остатки, движение денег и e2e вне задачи.
- Настройки и секреты — в `~/.ibmobile/<env>.properties`, изменяемые параметры — в ресурсах или `-D`. Реальные логины и `postman/` держать вне git.
  В логах и Allure сохранять исходные значения. Тестовые данные и процедуры Oracle готовит пользователь. Сохранить `Db` для вызова процедур.
- В отчёте указать число прошедших, упавших и пропущенных тестов с причинами, изменение строк всего и по коду/ресурсам/докам. Для Java — число строк до и после задачи.
- Коммит и пуш — только по команде «коммить и пуш», в `main`, сообщение на английском. Перед коммитом проверить секреты командой
  `git grep -nE "password=[^.<]|<реальный логин>"`. В отчёте указать, был ли коммит.
- Для `dependency:analyze` на Java 25 нужен плагин ≥ 3.9.0. Пометки unused для агрегатора `junit-jupiter` и используемых при запуске `allure-jupiter`, `ojdbc11` ожидаемы.

## Контуры, сессии и ошибки

- Бэкенд работает по HTTP. Dev поддерживает мультисессию и фиксированные коды. На preprod и prod одна сессия на логин.
  `@Login` принимает ключ файла контура. Профиль KILLER — только для личных запусков пользователя.
- Негатив логина — только несуществующий логин. Пять неверных паролей блокируют реальный профиль. Коды подтверждения не подбирать.
  Смена логина или пароля завершает сессию. Таким тестам нужен отдельный профиль, исходные данные восстанавливает сам тест.
- `HttpFilter` добавляет `uid` и ticket, явный ticket сохраняет. `.auth().none()` отключает автоматический ticket.
  Без ticket и с несуществующим ticket приходит `errorCode=1`, после логаута — 5. Сбой автоматического логаута виден в Allure, исход теста сохраняется.
- При HTTP 200 результат проверяет тест. На dev ограничение частоты запросов при логауте приходило в теле с `errorCode=403`.
  `error` сверяет точные `errorCode` и `errorDesc`, затем схему. Схема допускает код 2, ожидаемые `ErrorCode` — 1, 4, 5 и 1000.
  `rejected` ищет `badItem`, `errorMessage` и `error=true` в **одном** элементе `checkResult` и проверяет схему отказа.

## Документы и счета

- Каждому классу с `prepare_doc` нужен `@ResourceLock("prepared_doc")`. На логин один подготовленный документ на 5 минут для **всех ticket**.
  Его может перезаписать и негативный запрос. `send_doc` вызывается без id документа.
- `prepare_doc` с версии 7.6 принимает multipart. `DocContent.attach` добавляет части `file` и описания в `attachmentsList` до сериализации `doc_content`.
  Без `doc_type` наблюдали HTTP 500.
- `NONE` берёт `noneAuthInit.code`. Для `SMSPWD` порядок — `check_password/1.1` → `send_confirm_sms/1.1` → `send_doc` с двумя `secure` (SMS и PWD).
  `SCRETCH` требует активную скретч-карту. Вложенный `NO_ACTIVE_CARD` встречается при успешном `prepare_doc`. Коды — из файла контура. QR вне автоматизации.
- Деньги — `BigDecimal`, у позитивных переводов суммы 1.01–9.99 случайны. На dev документы копятся.
  «Подобный документ уже обрабатывается в банке.» — бизнес-отказ `send_doc`. Точное правило дубля неизвестно.
- У `ib_pay_rub` сумма в `amountDeb`. Сохранить регистр `RCliInn`, `RBankName`, `RBankBic`. Оба текущих кейса используют вложение и SMSPWD.
  У `ib_our_acc_transfer` сумма в `amount`, счета одной валюты.
- Термины счетов — дебетовый, кредитный, текущий, депозитный. В коде использовать `Type`. В `accounts.account` дебетовый с картами — `cardAcc && !isCredit`,
  кредитный — `isCredit`, текущий — `currAcc`, депозитный — `idepAcc`. У основного dev-профиля нет валютных дебетовых с картами и валютных кредитных.
- Для chargeback карту берём из `prior_info`, операцию — из шаблона пользователя. Операция `1` на dev давала `errorCode=2` при ожидаемой в `unknownOperation` схеме бизнес-отказа.
  Чужой валидный счёт в `acc_details` также давал код 2.

## Проверки и Allure

- Выполнить запрос до группы «Проверки». Внутри группы каждую проверку оформить именованным `Allure.step("…", () -> assertThat(...))`.
  AssertJ `.as(...)` описывает ошибку. `matchesSchema` уже создаёт шаг с путём схемы, `error` и `rejected` сами группируют проверки.
- Вход, выход, подтверждение и запросы за данными уже видны в HTTP-шагах. `success(response)` вызывается напрямую, в том числе при сборе образцов в `SchemaDraft`.
- Дерево и статусы шагов лежат в `target/allure-results/*-result.json`. Maven очищает результаты на `initialize`.
  `SchemaDraft` выводит типы и обязательные поля в `.schema-samples/`. Значения успешных статусов в эталонной схеме draft-04 закрепляют вручную.
